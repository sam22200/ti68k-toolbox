# Mode 7 - Demo 2 (David Coz, 2005): decompiled

The upstream is https://www.ticalc.org/archives/files/fileinfo/374/37446.html (`mode7.zip`, shipped without sources).
It is a TI-89 race demo in the style of F-Zero. The floor uses Mode 7 at two resolutions, with flat-shaded 3D objects along the road and collisions with the walls.
It was built with TIGCC 0.96 beta 5, in C with asm blocks.

**Controls**: left/right turn, [2nd] accelerates, [◆] brakes, [ESC] quits.

## How it works

- **Memory**: everything sits in a `Game` struct of 0x88E bytes on the stack.
  - Heap blocks hold two 128×128 textures (one byte per texel), the tiles at 16×16 and at 8×8, the sky, and a 240×128 two-plane virtual screen with the LCD layout.
  - That screen is copied to the gray planes with `movem` once per frame.
- **Floor**: the ship stays fixed on screen and the camera sits 60 units behind it.
  - The near floor (rows 60 to 99) samples a texture built from 8×8 map cells of 16×16 tiles. It is drawn at half resolution, every other line, and the lines are then doubled.
  - The far floor (rows 45 to 59) is drawn at full resolution. Its texture covers twice the area, built from 16×16 cells of 8×8 tiles; the tiles were shrunk at load time with random dithering.
  - Each frame rebuilds only one of the two textures, alternately.
  - Each row is one division (distance = constant / row) followed by a fixed-point walk along the row (`render.s`).
- **3D**: 19 instances of 5 models (76 vertices, 38 triangles) are placed at load time and registered in a 16×16 grid of cells.
  - Each frame keeps the non-empty cells inside a cone in front of the camera, and then their faces, each face once.
  - Vertices are projected once each, through a cache, and faces with a vertex behind the eye are dropped.
  - Triangles are filled flat in 4 greys, one span per line on each plane.
- **Physics**:
  - The turn rate drops with speed, the throttle gain comes from a table indexed by speed, and brake and air drag are both constants.
  - Collisions use 75 wall segments sorted into 8×8 cells: a ship that ends up behind a wall is put back on the wall's line.
- **Timer**: auto-int 5 counts the ticks, and the frame time is printed every 8 frames in the top-left corner.

## Verification

1. **Disassembly**: `mode7.s` reassembles to the 29,725 bytes of the original, with 0 differences (`tools/cmp.py`).
2. **asm routines** (`render.s`): all 8 routines, assembled alone, are identical to the original's bytes. The only differences are the PC-relative offsets to the moved tables and the `HLine` fix below.
3. **C**: it is written from the listing instruction by instruction, with 16-bit arithmetic wherever the original does 16-bit arithmetic. Compile-time checks enforce the structure offsets.
   - The disassembly compiled by TIGCC and the C compiled by GCC4TI do not produce the same code, so the check is on behaviour instead.
   - In the Titanium emulator both versions run the same key sequence (rest, 6 s of [2nd], 1.5 s of left). The screens match: the floor, the ship, and the 3D pyramids with their white and black halves.
   - The small differences in position come from the frame rate. The rebuild runs about as fast, with 1 to 2 ticks per frame.

## Bugs in the original, fixed in the rebuild (commented in the code)

- **Heap blocks used unlocked**: the original takes the pointers with `HeapDeref`, and then `GrayOn` calls `HeapAllocHigh`, which can compact the heap and move the blocks. The original escapes this by luck of its memory layout (the PPG launcher is in the heap too). In the rebuild the near texture was reading another block. Fix: `HLock` (`DerefAll`, `Deref3D`).
- **`HLine` damages `d3`**: it saves `d3` with `move.w`, then `moveq` wipes the high word. The original's caller only used the low word; GCC4TI's code keeps 32-bit values in `d3`, so the triangles came out striped. Fix: `move.l`.
- **`World.level` never set**: `Init3D` does not write it, so it holds whatever the stack contained (0 in practice). The rebuild sets it.
- Not fixed, only noted:
  - The 5,120-byte cell buffer is too small for 256 cells × 16 faces.
  - The timer start value is not restored at exit, although it is AMS's own value 0xCC.
  - The saved frame-time digits are uninitialised during the first 7 frames.

Rebuild pitfalls:
- AMS already defines `FillTriangle` as a ROM call and `off` as a macro, hence the names `FillTri` and `ofs`.
- `(d8,pc,Xn)` reaches only 127 bytes, and GNU as truncates the offset without an error, so `HLine`'s tables must stay right in front of it.

## Benchmark and optimisations

`make bench` builds `build/m7bench.89z`, and `tools/bench.py` runs it under `ti-cycles` (datasheet 68000 cycles, headless). Three scenarios, 16 or 160 frames each:
- **0**: start line, at rest;
- **1**: 8 distant "mountains", 16 triangles 600 to 960 world units ahead, covering 9.6 % of the view;
- **2**: full throttle from the start line.

For each scenario the script prints the cycles per frame of every zone and a checksum of the 128×100 view. `--ref base` compares with the original, which you get with `make bench BENCH_FLAGS=-DORIGINAL`. Every optimisation sits behind `#ifndef ORIGINAL`, so the faithful decompilation is still in the sources.

| cycles / frame | original | optimised |
|---|---|---|
| scenario 0 (start) | 666,518 | **362,430** (−46 %) |
| scenario 1 (distant 3D, 10 %) | 1,059,860 | **492,062** (−54 %) |
| scenario 2 (driving) | 686,896 | **414,938** (−40 %) |
| mode 7 far / near | 224k / 133k + 12k line copies | 137k / 125k |
| textures (at rest / driving) | 112k / 112k | 15k / 71k |
| clear + sky + copy to planes | 17k + 17k + 35k | 0 + 10k + 0 |
| 3D (scenario 0 / 1) | 93k / 487k | 61k / 190k |

At 12 MHz with the grayscale driver's ~9 %, that is about 16 → 30 fps at the start and 10 → 22 fps in the 3D scene.

The screens are identical to the original's, pixel for pixel. The only exception is the horizon rows 45 to 47, where the original samples outside its far texture (the window is narrower than the view) and reads whatever memory lies next to it. Verified on the Titanium in TiEmu: it drives, turns and quits.

What was done (details in the comments marked *optimised*):
- **Mode 7** (`render.s`, `Mode7FarFast`/`NearFast`):
  - One 32 KB block with 256-byte rows (near texture in columns 0..127, far in 128..255), so the index is `swap` + `move.b` with no shift.
  - Texels carry their plane bits at the top of the byte and are shifted into two byte accumulators (`add.b`/`addx.b`), then written once per 8 pixels. There is no colour compare chain, no `or.b` to memory, and no screen clear.
  - Near rows use 2 bits per texel, a nibble-doubling table, and the doubled line is written in the same loop.
  - The per-row divisions come from tables.
- **Textures**: rebuilt only when the window moves to another map cell.
- **Screen**:
  - GrayDBuf: drawing goes straight into the hidden planes, which are dark first; the data is swapped instead of the routines.
  - The sky is copied with `movem`, 16 bytes per row.
- **3D**:
  - The projection uses `muls.w`/`divs.w` instead of `__mulsi3` and the ROM's 32-bit division.
  - The scanline loop is in asm (`TriSpans`), with one copy per colour, both planes per span, and edges in registers. It is checked against the C loop on 2,000 random triangles (bench scenario 4).
  - A `memset` whose result is never read was dropped.
- **Ship physics**: `muls.w` where the operands fit 16 bits.

Still costly, if more is needed:
- **Floor**: about 66 cycles per sample, the floor for exact 16.16 stepping. Beyond that, 8.8 stepping or half-resolution far rows would help, but the pixels would change.
- **Texture rebuild while driving**: a toroidal texture would need a 64 KB block or one mask per sample.
- **Triangle spans**: about 400 cycles per line.
