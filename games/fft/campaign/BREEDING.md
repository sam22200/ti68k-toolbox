# World calendar and breeding backend (2026-11-14)

The reusable **backend** is implemented and checked. It is **not integrated**
into the shipping world map, FSV6, deployment, management or packages yet. The
Chapter I breeding prerequisite remains open. Current installed programs and
reviewed pictures are unchanged; use the story-choice release, not this fixture.

## Source and portable rules

The target is USA PS1. Local decomp source leads are
`wldcore_map_step_route_travel`, `wldcore_advance_calendar_day`,
`world_unit_update_monster_breeding`, `main_party_create_monster_egg`,
`main_unit_generate_out_of_battle`, `main_unit_generate_base_raw_stats` and
`main_party_level_unit_to_target`. `tools/breeding_rules.py` extracts a285-byte
FWB1 bank from the local disc. It contains the12 non-leap month lengths,13
inclusive zodiac limits,48 four-byte offspring/hatch rows, monster raw-stat
seeds/variance and12 birthday limits. All48 monster skill sets coincide exactly
with jobs94..141; extraction verifies this interval against the shared source
job table. The two calendar tables and both zodiac algorithms must agree.
No second job-growth/skillset table is added. Generated bytes remain local.

**SOURCE READ:** one calendar day advances after completing each location-to-
location route leg, before arrival events/random encounters. The route's
interpolation points and pathfinding cost are not extra days. March21 increases
script variable67, capped99; this is not a Gregorian year counter. The scripted
multi-day advance routine has different proposition/birthday rules and does
not loop over daily breeding: do not implement story time jumps by repeatedly
calling this backend without checking the original event requirement.

`breeding.h` performs one validated daily step:

1. Advance month/day; decrement existing eggs. A hatch gets today's birthday
   and zodiac. Units hatched in this scan cannot be parents/level donors today.
2. Build parent and non-egg level lists in source20-slot formation order,
   including occupied persistent guests. No parent means no random draw.
3. Draw low8 bits:0..5 rare,6..15 uncommon,16..31 common,32..255 no egg.
   There is one daily roll, not a per-monster roll or mating-pair requirement.
4. Select a parent uniformly, read its actual offspring row, then select the
   child's hatch days as `max(2, rand15 % offspring_range + 1)` and color0..3.
   The source ranges are3..9. Even a full ordinary roster consumes these four
   policy draws, then refuses creation without overwriting a unit or guest.
5. Generate the real child's name, Brave/Faith and five raw seeds now. Preserve
   the otherwise-overwritten random-birthday draw and retry duplicate ordinary
   monster names. Choose its level from the pre-existing non-egg list after
   generation. Append to the ordinary16-slot roster, never a guest slot.

Generation stores the existing SaveUnit level-one seed representation, with
raw-current clear, rather than growing five stats through every level during
travel. Existing stat restoration/growth owns that conversion. The child has
no equipment/JP/learned human abilities; `type3`, job-derived sprite and source
monster name index remain explicit. Hatch changes its birthday/zodiac, not its
species, level, seeds, name or Brave/Faith. The parent can subsequently disappear
without a reroll. The backend uses existing verified `muls16`; no new ASM.

## State and integration contract

`WorldParty` is a **proposed69-byte, byte-only payload**, not a new current Save
field:4 calendar/header bytes,20 packed initial/remaining egg timers,40 birthday
bytes and5 packed color bytes. Unknown birthdays are0; hatch birthdays are
BE1..365. Eggs count against the ordinary roster's16 slots. All20 formation
positions have metadata so guest reordering/recruitment can move it explicitly.
The move/clear helpers preserve timers, birthdays and colors. All actual
roster producers still need to bind them before enabling this feature.

Rules must pass cold `world_rules_valid` before any daily call. State validation
rejects invalid dates/levels, duplicate/invalid guest keys, absent-slot metadata,
zero/underflowed egg timers and non-monster eggs before date/RNG/party mutation.
An egg is presently represented by side metadata alongside a type3 SaveUnit:
**do not feed it to the current deployment/management code**, which does not
know that metadata yet. The backend allocates no heap or second Save; its two
bounded daily lists use40 stack bytes.69 proposed saved bytes is not a native
installed-RAM, stack-peak or full-frame performance certificate.

The caller supplies15-bit random draws. Retail reseeds from play-time fields;
portable clock/RNG binding and persistence are still an integration decision.
No callback, frame counter, entry or idle render may silently advance a day.
Keep the old FSV6 prefix/guest tail intact during migration; old saves cannot
reconstruct an elapsed date they never recorded. Resolve a documented start
date from the source chapter/event, rather than inventing elapsed travel.
