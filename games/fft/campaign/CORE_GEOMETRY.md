## Shared core and active integration

`tactical_grid.h` separates an8-bit node ID from x/z/layer. A512-address source
lookup has a separate presence bitmap; ID255 is valid on either floor. Node and
requested-target counts are16-bit. Dense lower rectangles use generated byte
row offsets without storing another512-byte lookup. Both forms expose the same
position/find contract and reject absent upper positions without overwriting
the caller's output ID. Coordinates, source addresses and compact IDs are not
interchangeable.

World/view conversion is shared with the existing battle projection. The4×18
fixture checks all four inverse conversions and an asymmetric landmark. It does
not certify upper-floor sprite heights/cover, which are still adapter work.

`tactical_search.inc` implements the existing movement costs and stable FIFO
order on a graph. A leap names its actual intermediate node: it never averages
two compact IDs. The current map builder produces those explicit references;
the movement/AI spread calls the common search. Existing masks, blockers, water
costs and tie order are retained. A12-byte cost table avoids repeated Boolean
arithmetic in the inner loop. Fixed Work-row bindings give the compiler shifts
and known addresses; the fixture backend reads the same algorithm through a
dynamic graph view.

The four Dial queues have256 backing slots each. Their counters may remain8-bit:
positive costs never requeue the origin, and tentative improvements differ by
at most two for costs1..3, so a node cannot occupy the same bucket twice before
reset. At most255 non-origin IDs can occupy one bucket. This bound does **not**
reduce the graph's256 valid IDs or its16-bit requested-node count. Graph validation
checks destination/via IDs, edge sizes and flags. The resident map builder already
guarantees these inputs and calls the trusted initializer once per search.

Search cost bytes retain255 for unreachable; supported search limits are0..254.
This is a distance value, not an invalid tile identity. Current battle limits are
ordinary Move and the existing124-step AI flood. Teleport/Fly/Float and source
upper-floor movement rules are not implemented by giving a graph more nodes.

Path extraction is bounded by the node count, rejects cycles/bad predecessors
and checks output capacity before writing. Current `make_path` uses it and
looks up coordinates rather than dividing every node ID by map width. Invalid
unit/target coordinates are rejected. Its reviewed16-position animation buffer
is unchanged; future streamed/long paths remain a separate gate.

The loader now rejects unsupported width/height/scene spans and truncated tile
arrays before constructing Work. A compile-time guard rejects enlarging the old
adapter past255 slots until all count/cursor APIs are migrated.

## Native packaging and save ownership

The first expanded executable exceeded TTPack's64936-byte input limit. Save data
previously embedded3138 zero bytes in the save code overlay. It now occupies a
tail in the existing longer-lived battle allocation:1494-byte State plus3138-byte
Save, **4632 bytes** total. The module's largest image drops to8868 bytes, so the
packed battle fits again. The serialized Save remains3138 bytes, FSV3 unchanged.

`rt_save` on TI borrows its source until runtime teardown. That tail survives
the victory release of Work/view/actor buffers and any overlay eviction, then
the final exit handler frees the allocation. It must never use the background
cache or other Work memory as its pending save buffer. Native flow fixtures
check this ownership and the saved bytes after the real handoff. The common
save layout is in `save_types.h`; file helpers are included after module context
bindings. Module signatures now also include the Save size.

Current native Work is44434 bytes, +1648 from the preceding capacity milestone.
The four requested heap blocks are4632,32320,60594 and10176 bytes: **107722 bytes**,
up4786. This excludes supervisor/code/modules/grayscale, allocator overhead and
stack; it is not a measured combined heap high-water. The largest block is60594.
Maximum-map storage will need another layout measurement before integration.
